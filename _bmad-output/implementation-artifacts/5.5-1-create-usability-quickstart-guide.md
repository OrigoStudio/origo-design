# Story 5.5.1: Create Usability Quickstart Guide

## Story Foundation

**User Story Statement:**
As a Developer,
I want a comprehensive Quickstart/Usability guide detailing end-to-end user workflows,
So that I understand the actual user perspective and have clear documentation on how the system is intended to be used.

**Acceptance Criteria:**
- **Given** the current state of the Origo platform after Epic 5
- **When** a developer or QA engineer needs to test or interact with the system end-to-end
- **Then** they have a detailed Quickstart guide documenting the entire usability flow
- **And** the guide clearly covers the "happy path" and core use cases from an end-user perspective.

**Business Context and Value:**
This documentation acts as the foundational knowledge for developers and QA engineers to understand the system end-to-end. Without it, technical testing lacks user context. It is essential for defining QA protocols (Story 5.5.2) and validating the "10-minute onboarding" objective (NFR-DX-001).

---

## Developer Context

**Dev Agent Guardrails & Technical Requirements:**
- **Target Audience:** Write strictly from the perspective of an Application Developer (The Primary Consumer) as defined in the PRD.
- **The "Happy Path" Workflow:** The guide MUST explicitly document the following sequence as the core happy path:
  1. Scaffold a project using the CLI (`origo init`).
  2. Define an entity using BADL (`origo generate entity`).
  3. Compile the schema into the canonical AST via the core engine (`origo validate`).
  4. Preview the rendered UI via the Web Adapter in the browser Playground.
- **10-Minute Onboarding Benchmark (NFR-DX-001):** Ensure the documented workflow can be realistically executed by a net-new developer in under 10 minutes.
- **QA Protocol Alignment:** Write each step as a concrete, testable action. This guide serves as the direct input for Story 5.5.2 (Establish QA Protocols), so ambiguity will break downstream QA workflows.
- **Formatting Constraints:** Use active voice, clear numbered lists for steps, and keep paragraphs concise.

**Architecture Compliance:**
- **Starlight Specifics (P1-AD-8):** 
  - The file MUST include standard Astro/Starlight markdown frontmatter (e.g., `title`, `description`).
  - Use built-in Starlight Aside components (`:::note`, `:::tip`, `:::caution`) to highlight important developer context.
- The documentation format must be strictly compatible with Astro Starlight (Markdown/MDX).

**File Structure Requirements:**
- **[NEW]** `apps/docs/src/content/docs/getting-started/quickstart.md` (This path is strict, do not deviate).

**Testing Requirements:**
- Validate that the exact sequence of commands and steps defined in the happy path is functionally accurate based on the current state of the Origo CLI and Core platform.
