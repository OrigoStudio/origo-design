## 1. Executive Summary

Epic 1 focused on building the fundamental UI primitives and layout blocks required for Origo Design's Angular 18 renderer. All 6 planned stories were completed and delivered with standalone components powered by Angular Signals, strictly abiding by the `InteractionContract` and `OrigoAdapter` architecture. 

During the retrospective, the team recognized that while the functional deliverables provide a strong and necessary baseline, code reviews were heavily burdened by preventable architectural and styling non-compliances (such as hardcoded CSS values, missing Shadow DOM encapsulation on layout items, and superficial test suites). To prevent recurring friction in upcoming epics, Project Lead Patel directed that modular, developer-facing documentation and checklists be established prior to commencing Epic 2.

## 3. Retrospective Analysis

### What Went Well (Successes)
- **Foundational Coverage:** All core primitives and layout components needed for future business forms and views were established cleanly.
- **Idiomatic Architectural Contract:** The `InteractionContract<T>` and `OrigoAdapter<T>` contract pattern scaled well across both simple buttons and complex controls.
- **Modern Angular Adoption:** Standardized on Angular 18 Standalone components, Signals (`input()`, `computed()`), and zoneless change detection patterns.
- **Shadow DOM Testing Baseline:** Formulated consistent patterns for piercing Shadow DOM boundaries (`fixture.nativeElement.shadowRoot ?? fixture.nativeElement`) in Jest test suites.

### Challenges & Growth Areas
- **Architectural Omissions in Early Drafts:** In multiple stories (notably Story 1.5), components initially lacked required invariants such as `ViewEncapsulation.ShadowDom`, `ChangeDetectionStrategy.OnPush`, and `contractSchema`.
- **Styling Standards Non-Compliance (AD-6):** Multiple instances of hardcoded CSS values, missing `--origo-*` design tokens, and physical CSS properties (instead of CSS logical properties like `padding-inline`) were caught late during code reviews.
- **Complex Component Boundary Issues:** Story 1.6 faced major hurdles with `document.execCommand` deprecation inside Shadow DOM and drag flickering in Dropzones.
- **Superficial Unit Testing:** Several test suites originally bypassed real DOM interactions and relied on shallow mocks, requiring rework during review.

### Key Insights
- **Upfront Reference Documentation:** Developers need concise, dedicated reference docs (specifically separating SCSS/tokens from component invariants) to refer to during development rather than relying solely on post-implementation code reviews.
